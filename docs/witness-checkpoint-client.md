# Authenticated checkpoint refresh client

The optional `sociacl-ids/checkpoint-client` export provides
`openWitnessCheckpointClient(options)` for the existing-state refresh path in
[#136](https://github.com/FyberLabs/SociACL/issues/136). It connects an authenticated
management HTTPS exchange to the [durable checkpoint store](witness-checkpoint.md#continuity-reconciliation-and-browser-refresh).
It does not implement a server route, enrollment, recovery or root migration.

## Independently trusted configuration

Supply all checkpoint-store options: database name, independent management and
policy roots, root epoch, audience, enrolled client, revision floor, trusted UTC
clock and optional monotonic clock. Also supply:

- `url`: an absolute HTTPS management endpoint without userinfo, query or fragment.
- `getAccessToken(signal)`: an asynchronous provider for a management enrollment
  bearer credential. It must honor cancellation where possible. The provider and
  credential scope must be provisioned independently of downloaded responses.
- Optional `timeoutMs`: integer 1–60,000 milliseconds, default 10,000.
- Optional `fetch`: trusted platform injection, not an untrusted extension point.

The credential must authorize the enrolled client to request deployment policy
refresh. An ordinary account login, wallet proof or OIDC token does not itself
supply deployment-wide trust/recovery authorization. The server must authenticate
and authorize it, match its enrollment to the requested client/audience/epoch,
and obtain current complete history under the management serialization boundary.
No server authorization is inferred from a successful browser test.

```js
import { openWitnessCheckpointClient } from 'sociacl-ids/checkpoint-client';
const client = await openWitnessCheckpointClient({
  ...independentlyProvisionedStoreOptions,
  url: managementEndpoint,
  getAccessToken: signal => managementSession.accessToken({ signal }),
});
await client.refresh();
const state = await client.readFresh();
// Use at the positive-authorization boundary with separately fresh account history.
```

Opening and historical reads perform no network request. Missing or corrupt state
refuses refresh before credentials or transport are invoked. There is no bootstrap
fallback. Provisioning first state and authorizing recovery remain separate work.

## Refresh HTTP contract v1

The client posts UTF-8 JSON with exactly these fields:

```text
{ type: "sociacl-witness-checkpoint-request-v1",
  operation: "refresh", challenge, client, audience, rootEpoch }
```

`challenge` is generated by the store using 32 unpredictable bytes. It is bound to
one in-memory request, never restored after restart. The request is not signed by
the browser; the management credential authenticates the caller. The service must
reject unauthorized operations and scope, never reinterpret refresh as enrollment,
restore or migration. This wrapper introduces no new signature domain; the response
checkpoint retains the [v1 signed format](witness-checkpoint.md).

Requests use `Authorization: Bearer <token>`, `Accept: application/json` and
`Content-Type: application/json`. Cookies and referrers are omitted; redirects are
refused. Fetch uses `cache: no-store`. Credentials remain in the authentication
provider/HTTP exchange and are not written into policy storage. Tokens must match
bearer-token syntax and be at most 8,192 characters. Provider/transport exceptions
are replaced with a generic refresh failure so their messages cannot leak tokens.
Normal browser TLS checks remain enabled. Cross-origin deployments must configure
CORS for the exact application origin, POST and these headers; the library does
not bypass CORS or use ambient cookies.

A successful response is HTTP 200 with `Content-Type: application/json` (parameters
allowed), and UTF-8 JSON containing exactly:

```text
{ type: "sociacl-witness-checkpoint-response-v1",
  checkpoint: "<exact signed checkpoint envelope JSON text>",
  policy: "<exact matching signed policy envelope JSON text>" }
```

Keep each envelope as a string so its signed bytes are preserved. Duplicate members,
unknown fields, invalid UTF-8, missing strings, redirects, 304 and other non-200
responses are rejected. The response body is limited to 4,194,304 bytes, inclusive,
including JSON escaping/whitespace. Declared length is checked before streaming;
actual bytes are bounded independently. Existing inner envelope/schema/signature
limits still apply. Providers must encode within both outer and inner limits.
The server should return `Cache-Control: no-store`; the client does not use cache
headers as a freshness authority.

## Failure, cancellation and freshness

`refresh({signal})` invalidates this client's previous lease immediately. A new
refresh supersedes and cancels its previous operation. An old failure or late
response cannot cancel a newer successful lease. Credentials, download, durable
installation and the final fresh read are all covered by the operation timeout;
an overdue timer cannot accept a response after an event-loop stall. Uncooperative
credential providers/streams cannot keep the public refresh promise pending forever.
Late HTTP bodies are cancelled and never installed.

Only successful durable installation and a final freshness check return state.
Transport, authentication, timeout, schema, signature, continuity or storage failure
rejects; no stale trust fallback or automatic retry is provided. `readInstalled()`
retains historical evidence. `readFresh()` uses the store's earlier policy/checkpoint
UTC expiry and request-anchored monotonic deadline. Use it at each freshness-sensitive
decision boundary; retaining an earlier returned object does not retain a lease.

`cancel()` invalidates this handle's active operation and lease; `close()` also
closes storage. The caller's abort signal applies until that refresh finishes;
it does not revoke a later independent operation. Cancellation/timeout after a
transaction commits can leave new evidence installed without granting freshness.
Inspect historical state and issue a new refresh; never repeat the old challenge.
Reopening requires a new request regardless of the saved signatures' expiry.

Historical reads and current-key offline revocation remain separate: a missing
freshness lease blocks positive authorization, not the creation, retention or
application of a verified restrictive revoke. Account history freshness and
present-revocation checks are not supplied by this transport.

## Validation and remaining adoption

The client regression suite covers authenticated request binding, replay, restart,
missing state, credentials, malformed/oversized responses, deadline/abort behavior,
late responses, supersession and post-commit cancellation. Real Chromium acceptance
uses a temporary test-only TLS certificate and public fixture signing keys to test
actual HTTPS POST, durable installation, replay/outage/redirect/stall failures,
cookie/referrer omission and full-process restart/renewal. Run the canonical
`bash scripts/test-all.sh` and `npm run test:browser-store` with Node 24+ and Chromium.

These tests establish client behavior. Management issuance and protected continuity,
explicit enrollment/recovery/root-migration authorization, actual application
startup/resolver integration and deployed acceptance remain #136 and
[FyberLabs/panopticon#552](https://github.com/FyberLabs/panopticon/issues/552).
